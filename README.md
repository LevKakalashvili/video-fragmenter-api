# Video Fragmenter Service (Сервис фрагментации видеофайлов)

Микросервис предназначен для **высокопроизводительного разбиения видеофайлов на чанки**
с последующей загрузкой чанков в S3-совместимое хранилище и публикацией прогресса 
обработки в Kafka.

Основная цель MVP — **максимальная производительность обработки** при предсказуемом 
потреблении ресурсов и возможности горизонтального масштабирования.

Сервис работает как **выделенный Kafka worker**: читает задания батчами, 
обрабатывает видео внутри инстанса с контролируемым параллелизмом и публикует 
события прогресса наружу.

------------------------------------------------------------------------

# 1. Основные требования

## Функциональные

Сервис должен:

1. Получать задачи на обработку из **Kafka**
2. Загружать исходный видеофайл из **S3/MinIO**
3. Разбивать видео на чанки
4. Загружать чанки обратно в **S3/MinIO**
5. Отправлять события прогресса и финальный статус в **Kafka**
6. Обрабатывать сообщения **батчами**
7. Ограничивать параллелизм на двух уровнях:
   - количество видео, одновременно обрабатываемых в одном инстансе
   - количество chunk-процессов внутри одного видео

------------------------------------------------------------------------

## Ограничения MVP

| Параметр | Значение |
|:--|:--|
| Формат видео | только **MP4** |
| Максимальный размер файла | **500 MB** по умолчанию |
| Тип фрагментации | **по времени** |
| Размер чанка | приходит **в Kafka сообщении** или используется значение по умолчанию |
| Режим фрагментации | **fast keyframe aligned** |
| Обработка задач | **batch consume из Kafka** |
| Внутреннее состояние | **in-memory в рамках обработки инстанса** |
| Источник статуса для внешних систем | **Kafka events** |

# 3. Основные архитектурные принципы

## 3.1 Отдельный worker-сервис


Ключевые решения:

-   **FFmpeg без перекодирования**
-   **Chunk upload сразу после появления**
-   **Удаление локальных файлов после загрузки**
-   **Параллельная обработка файлов**
-   **Параллельная загрузка чанков**
```text
Kafka -> download -> fragment -> upload -> Kafka events
```

Текущая граница ответственности в коде:

- `VideoJobService` отвечает за orchestration: download, построение chunk jobs, state, progress events, manifest, cleanup временной директории задачи.
- `FfmpegChunkExecutionService` отвечает только за выполнение одного chunk: build command, subprocess, проверка output, normalized result/error.
- `S3ChunkUploadService` отвечает только за upload одного готового chunk: build chunk key, upload, cleanup локального файла, normalized result/error.
- `S3ManifestService` отвечает только за сборку и upload manifest.json: build payload, manifest key, JSON serialization, normalized result/error.
- `FfprobeVideoProbeService` отвечает только за анализ локального видеофайла через ffprobe: build command, subprocess, parsing, metadata validation, normalized result/error.
------------------------------------------------------------------------

## 3.2 Batch consume из Kafka

Сервис читает сообщения **пачками**, а не по одному.

Это уменьшает:

- число сетевых round-trip к Kafka
- накладные расходы на poll loop
- стоимость диспатчинга задач

Но batch consumption сам по себе **не означает**, что все сообщения из батча 
сразу запускаются в обработку. После чтения батча задания попадают во внутреннюю 
очередь и обрабатываются с ограничениями `K` и `M`.

------------------------------------------------------------------------

## 3.3 Два уровня ограничения параллелизма
Чтобы сервис не перегружал CPU, диск и сеть, вводятся два обязательных ограничения.
### Ограничение `K` — видео на инстанс
`K` = максимальное количество видео, которые один инстанс сервиса может 
обрабатывать одновременно.
Пример:
```text
K = 2
```
Это означает, что даже если из Kafka пришел батч из 20 сообщений, одновременно 
будут реально обрабатываться только 2 видео, а остальные останутся во внутренней 
очереди.
### Ограничение `M` — chunk-процессы на одно видео
`M` = максимальное количество chunk subprocess / ffmpeg-задач, которые можно 
запускать одновременно для одного видео.
Пример:
```text
M = 3
```
Если видео разбилось на 30 чанков, это **не значит**, что будут запущены 30 процессов
сразу. Одновременно выполняются только 3, остальные ждут освобождения слота.

------------------------------------------------------------------------

## 3.4 Backpressure обязателен
Контроль нагрузки обеспечивается через:

- внутреннюю очередь video jobs
- лимит `K` на число видео в работе
- лимит `M` на число chunk-процессов на видео
- ограничение параллельной загрузки чанков в S3
- ограничение размера Kafka batch

Без этих ограничений архитектура быстро деградирует под нагрузкой.

------------------------------------------------------------------------

## 3.5 Event-driven pipeline
Внешняя интеграция строится на событиях Kafka:

```text
Kafka job event
      ↓
video processing
      ↓
chunk_uploaded events
      ↓
completed / failed event
```

В MVP Kafka является основным способом сообщать наружу о ходе обработки.

------------------------------------------------------------------------

# 4. Общая архитектура сервиса

## 4.1 Логическая схема

```text
                    Kafka
                      │
                      ▼
             video-fragmenter-worker
                      │
        ┌─────────────┼─────────────┐
        │             │             │
        ▼             ▼             ▼
   In-memory       S3/MinIO      Kafka
   scheduler       chunks         status events
   + limits        storage
```

------------------------------------------------------------------------

## 4.2 Архитектура одного инстанса

```text
+=======================================================+
|                 INSTANCE                              |
+=======================================================+
| Kafka poller                                          |
|   getmany(max_records=N)                              |
+-------------------------+-----------------------------+
                          |
                          v
+-------------------------------------------------------+
| Internal queue                                         |
| [video_job_1, video_job_2, video_job_3, ...]          |
+-------------------------+-----------------------------+
                          |
                          v
+-------------------------------------------------------+
| Scheduler                                              |
| checks global limit: K videos                         |
+-------------------------+-----------------------------+
                          |
          +---------------+---------------+
          |                               |
          v                               v
+----------------------------+  +----------------------------+
| Video Worker Slot #1       |  | Video Worker Slot #2       |
| file_id=A                  |  | file_id=B                  |
| chunk concurrency = M      |  | chunk concurrency = M      |
+-------------+--------------+  +-------------+--------------+
              |                               |
              v                               v
     +-------------------+          +-------------------+
     | chunk proc pool   |          | chunk proc pool   |
     | max M processes   |          | max M processes   |
     +-------------------+          +-------------------+
```

Где:

- `K` — лимит на количество одновременно обрабатываемых видео в одном инстансе
- `M` — лимит на количество chunk-процессов внутри одного видео

------------------------------------------------------------------------

## 4.3 Полная схема потока с ограничениями

```text
+----------------------+
|       Kafka          |
|   topic: video_jobs  |
+----------+-----------+

+-------------------------------+

|-------------------------------|
| Kafka Consumer                |

+-------------------------------+
           |

+-------------------------------+

+-------------------------------+
           |
           v
+-----------------------------------------------+

| example: K = 2                                |
+-------------------+---------------------------+
                    |
         +----------+----------+
         |                     |

| file_id=...      |   | file_id=...      |

+--------+---------+   +--------+---------+

         | split into chunks    | split into chunks
         v                      v
+----------------------+   +----------------------+
| chunk_00001          |   | chunk_00001          |
| chunk_00002          |   | chunk_00002          |
| chunk_00003          |   | chunk_00003          |
| ...                  |   | ...                  |
+----------------------+   +----------------------+
         |                      |
         v                      v
+-----------------------------------------------+
| Limit: M chunk processes per video            |

+-----------------------------------------------+
         |
         v
+------------------------------------------------------+
| Bounded Process Pool / Subprocess Pool               |
|------------------------------------------------------|

+------------------------------+

+------------------------------+
```

# 5. Поток обработки видео

## 5.1 Последовательность обработки

```text
Kafka message
      │
      ▼
message попадает во внутреннюю очередь
      │
      ▼
scheduler ждет свободный video slot (лимит K)
      │
      ▼
HEAD request (S3)
проверка размера
      │
      ▼
download video
S3 -> local tmp
      │
      ▼
ffprobe
получение duration
      │
      ▼
split into chunk jobs
      │
      ▼
chunk scheduler
ограничение M subprocess на видео
      │
      ▼
ffmpeg chunk subprocess
      │
      ▼
upload chunk -> S3
      │
      ▼
Kafka progress event
      │
      ▼
delete local chunk
```

После завершения всех чанков:

```text
manifest.json
upload -> S3
Kafka completed event
safe commit Kafka offset
cleanup tmp directory
```

------------------------------------------------------------------------

## 5.2 Что считается завершением job

Kafka offset по сообщению о видео подтверждается **только после полного 
завершения всей обработки видео**, то есть когда:

1. все чанки успешно созданы
2. все чанки загружены в S3
3. опубликованы необходимые Kafka events
4. сформирован и загружен `manifest.json`
5. локальные временные данные очищены

Это дает понятную и безопасную модель подтверждения обработки:

```text
1 Kafka message = 1 fully completed video job
```

------------------------------------------------------------------------

## 5.3 Следствие такой модели

Плюс:

- простая и понятная семантика подтверждения
- внешним системам удобно мыслить сущностью "одно сообщение = одно видео"

Минусы:

- при падении инстанса возможно повторное выполнение всего video job
- retry отдельного чанка внутри видео сложнее, чем в архитектуре 
`1 chunk = 1 Kafka message`

------------------------------------------------------------------------

# 6. Kafka сообщения

## Входящее сообщение (job)

```json
{
  "file_id": "uuid",
  "input": {
    "bucket": "raw",
    "key": "videos/a.mp4"
  },
  "output": {
    "bucket": "chunks",
    "prefix": "videos/a/"
  },
  "chunking": {
    "type": "time",
    "seconds": 10,
    "mode": "fast_keyframe_aligned"
  },
  "limits": {
    "max_bytes": 524288000
  }
}
```

Описание полей:

```python
{
    "file_id": "uuid",  # Идентификатор исходного видеофайла.
    "input": {
        "bucket": "raw",  # Bucket, где лежит исходный файл.
        "key": "videos/a.mp4",  # Путь к исходному видео внутри bucket.
    },
    "output": {
        "bucket": "chunks",  # Bucket для сохранения чанков.
        "prefix": "videos/a/",  # Префикс, внутри которого будут созданы чанки и manifest.
    },
    "chunking": {
        "type": "time",  # В MVP поддерживается только time fragmentation.
        "seconds": 10,  # Размер одного чанка в секундах.
        "mode": "fast_keyframe_aligned",  # Быстрый режим без перекодирования, разрез по keyframes.
    },
    "limits": {
        "max_bytes": 524288000,  # Максимальный допустимый размер входного файла в байтах.
    },
}
```

Примечание по модели и обработчику:

- поле `job_id` не ожидается во входящем сообщении
- `job_id` формируется самим сервисом при начале обработки
- `job_id` используется в логах, временных путях и исходящих Kafka events

------------------------------------------------------------------------

## Progress event

Отправляется на каждый успешно загруженный чанк.

```json
{
  "job_id": "uuid",
  "file_id": "uuid",
  "status": "chunk_uploaded",
  "chunk_index": 7,
  "chunk_key": "videos/a/chunk_00007.mp4",
  "chunks_done": 8,
  "chunks_total_estimate": 42,
  "ts": "2026-03-05T12:34:56Z"
}
```

Описание полей:

```python
{
    "job_id": "uuid",  # Уникальный идентификатор текущей обработки видео.
    "file_id": "uuid",  # Идентификатор исходного файла.
    "status": "chunk_uploaded",  # Статус прогресса: очередной чанк успешно загружен.
    "chunk_index": 7,  # Порядковый индекс чанка, начиная с 0.
    "chunk_key": "videos/a/chunk_00007.mp4",  # Путь к чанку в S3 / MinIO.
    "chunks_done": 8,  # Количество уже готовых и загруженных чанков.
    "chunks_total_estimate": 42,  # Оценочное количество чанков по duration / chunk_seconds.
    "ts": "2026-03-05T12:34:56Z",  # Время публикации события в UTC.
}
```

# 7. In-memory модель состояния внутри инстанса

В текущей архитектуре состояние обработки не хранится в Redis и не отдается через API. Оно нужно только для координации выполнения внутри процесса.

## Что хранится локально в памяти

Для каждого активного `video job` инстанс держит в памяти структуру вида:

```python
{
    "job_id": "uuid",
    "file_id": "uuid",
    "status": "running",
    "chunk_seconds": 10,
    "chunks_done": 7,
    "chunks_total_estimate": 42,
    "started_at": "2026-03-05T12:30:00Z",
    "updated_at": "2026-03-05T12:34:56Z",
    "tmp_dir": "/tmp/<job_id>",
    "error": None,
}
```

Это состояние:

- не является внешним контрактом
- не переживает рестарт инстанса
- используется только для планирования, логирования и контроля завершения job

# 8. Видео фрагментация

Используется **FFmpeg segment muxer**.

```bash
ffmpeg -hide_banner -loglevel error \
  -i input.mp4 \
  -map 0 \
  -c copy \
  -f segment \
  -segment_time <seconds> \
  -reset_timestamps 1 \
  -segment_format mp4 \
  chunk_%06d.mp4
```

------------------------------------------------------------------------

## Почему это быстро

- нет перекодирования
- используется `stream copy`
- разрез выполняется по keyframes

Ориентировочно:

| Метод | Скорость |
|:--|:--|
| re-encode | ~0.5x realtime |
| copy + segment | **20-50x realtime** |

# 9. Производительность и ограничения нагрузки

## 9.1 HEAD перед download

`S3 HEAD` позволяет не скачивать слишком большие файлы.

------------------------------------------------------------------------

## 9.2 Ephemeral storage

Видео скачивается во временную директорию:

```text
/tmp/{job_id}
```

Это проще и стабильнее для ffmpeg, чем пытаться фрагментировать напрямую из S3.

------------------------------------------------------------------------

## 9.3 Upload чанков сразу после готовности

```text
chunk created
    ↓
upload
    ↓
Kafka progress
    ↓
delete local chunk
```

Это уменьшает размер локального временного хранилища.

------------------------------------------------------------------------

## 9.4 Ограничение числа видео в работе

Ограничение:

```text
MAX_VIDEOS_IN_PROGRESS = K
```
Нужно, чтобы один инстанс не начал одновременно обрабатывать слишком много 
тяжелых файлов.

------------------------------------------------------------------------

## 9.5 Ограничение числа chunk-процессов на видео

Ограничение:

```text
MAX_CHUNK_PROCESSES_PER_VIDEO = M
```

Нужно, чтобы одно большое видео не заняло все CPU / disk ресурсы инстанса.

------------------------------------------------------------------------

## 9.6 Ограничение параллельной загрузки чанков

Ограничение:

```text
MAX_UPLOAD_CONCURRENCY
```

Нужно, чтобы сервис не перегружал сеть и S3-хранилище.

------------------------------------------------------------------------

## 9.7 Формула верхней границы нагрузки

Если:

- `I` — число инстансов сервиса
- `K` — число видео одновременно на инстанс
- `M` — число chunk-процессов на видео

то верхняя граница числа одновременно работающих chunk-процессов в системе:

```text
I * K * M
```

Пример:

```text
I = 4
K = 2
M = 3
=> максимум 24 chunk-процесса одновременно
```

Это делает нагрузку на кластер предсказуемой.

# 11. Плюсы и минусы выбранной архитектуры

## Плюсы
- простой и понятный worker lifecycle
- хорошая производительность за счет batch consume
- ускорение обработки одного видео за счет параллельной обработки чанков
- горизонтальное масштабирование через Kafka partitions и число инстансов
- нагрузка контролируется через `K` и `M`

------------------------------------------------------------------------

## Минусы и риски

- retry одного отдельного чанка сложнее, чем при модели `1 chunk = 1 Kafka message`
- подтверждение Kafka offset происходит только после завершения всего видео
- при падении инстанса возможно повторное выполнение полного video job
- при неудачной настройке `K` и `M` легко упереться в CPU, disk I/O или сеть
- observability должна быть хорошо продумана, иначе тяжело разбирать деградации

------------------------------------------------------------------------

# 12. Ограничения MVP

| Ограничение | Причина |
|:--|:--|
| Поддерживается только mp4 | упрощение MVP |
| Только time-fragmentation | упрощение реализации |
| Keyframe aligned | максимальная скорость |
| Размер файла до 500 MB | ограничение ресурсов |
| Нет внешнего API статусов | worker-only архитектура |
| Нет постоянного state storage | в MVP достаточно Kafka events |

------------------------------------------------------------------------

# 13. Расширяемость архитектуры

В будущем возможно:

- добавление внешнего state storage
- отдельный API / status-service для чтения статусов
- retry pipeline для отдельных чанков
- переход на архитектуру `1 chunk = 1 Kafka message`
- DLQ / retry topics
- idempotency keys
- pause / resume partition при перегрузке

Также можно добавить дополнительные fragmenter-ы.

| Fragmenter | Описание |
|:--|:--|
| TimeFragmenter | по времени, равные интервалы времени; реализован в MVP |
| CustomTimeFragmenter | произвольные временные интервалы |
| FrameFragmenter | по количеству кадров |
| SizeFragmenter | попытка получить чанки примерно целевого размера |
| KeyframeFragmenter | резка по GOP / ключевым кадрам |

# 14. Основные конфигурационные параметры

| Параметр | Описание |
|:--|:--|
| `KAFKA_BATCH_SIZE` | максимальное число сообщений, читаемых из Kafka за один poll |
| `KAFKA_POLL_TIMEOUT_MS` | timeout для batch poll из Kafka |

# 15. Установка FFmpeg для локальной разработки (Windows)

Для локального запуска сервиса `ffmpeg` должен быть доступен в `PATH`.

В проекте используется portable-вариант FFmpeg в папке репозитория.

1. Скачайте Windows-сборку FFmpeg (zip) и распакуйте в:

```text
tools/ffmpeg/
```

Ожидаемая структура:

```text
tools/ffmpeg/bin/ffmpeg.exe
tools/ffmpeg/bin/ffprobe.exe
```

2. Подключите FFmpeg в текущую PowerShell-сессию:

```powershell
. .\scripts\dev.ps1
```

Скрипт добавит `tools\ffmpeg\bin` в `PATH` и выведет версию FFmpeg.

3. Альтернативно можно использовать Make-команду:

```text
make ffmpeg-dev-win
```

4. Проверка:

```powershell
ffmpeg -version
ffprobe -version
```

`tools/ffmpeg/` добавлен в `.gitignore`, поэтому бинарники не попадут в Git.

# 16. Установка Chocolatey и make (Windows)

Для запуска команд вида:

```text
make run-worker
make ffmpeg-dev-win
```

на Windows нужен установленный `make`.

## 1) Установить Chocolatey

Откройте PowerShell **от имени администратора** и выполните:

```powershell
Set-ExecutionPolicy Bypass -Scope Process -Force
[System.Net.ServicePointManager]::SecurityProtocol = [System.Net.ServicePointManager]::SecurityProtocol -bor 3072
iex ((New-Object System.Net.WebClient).DownloadString('https://community.chocolatey.org/install.ps1'))
```

Проверьте установку:

```powershell
choco --version
```

## 2) Установить make

В том же PowerShell:

```powershell
choco install make -y
```

После установки перезапустите терминал и проверьте:

```powershell
make --version
```

Если `make` не находится, откройте новый PowerShell или перезайдите в систему, чтобы обновился `PATH`.
